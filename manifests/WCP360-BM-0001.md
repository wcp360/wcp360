### DB-MV01 — Typed identifier grammar conflicts with approved API error codes

Database Global physical rules / Identifiers applies ^[a-z][a-z0-9_.-]{1,127}$ to typed registries and includes error_code in the typed namespaces. jobs.error_code, job_attempts.error_code and related fields use typed error registry IDs. The approved API v1.0 (blob 4893c5191b4928ecfa5a70f4dc14b39a8939fcea) explicitly defines IDEMPOTENCY_CONFLICT and UNKNOWN_OUTCOME; the DB contract itself also uses uppercase errors. The universal lowercase grammar cannot validate those values.

Required owner resolution: specify namespace-specific grammar or explicit exceptions preserving exact canonical API error codes. Do not lowercase/rename API codes or conflate contract_id with ipc_operation_id. QA must check accepted canonical uppercase errors and rejected unknown codes.

### DB-MV02 — Session surface isolation lacks a concrete persistence mapping

Security v1.0 (blob 6d74f2f363524511424f839ca7262143c2af95ab) requires separate origin, cookie name, server-side session namespace, surface claim and runtime Unix identity for USER and ADMIN. Database wcp_iam.sessions specifies session_id/user_id/secret_verifier/state/auth_strength/times but no surface or namespace field, separate relation, or explicit binding to a separate canonical session store.

Required Database + Security resolution: define the physical representation/enforcement or identify an exact approved external-store mapping; spell out how a USER session cannot authenticate on ADMIN and vice versa. This is an unresolved mapping, not evidence of an implemented vulnerability. QA must cover wrong-surface session lookup/validation.
